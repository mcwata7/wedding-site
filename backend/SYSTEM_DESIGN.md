# Wedding Planning Backend — Implementation Design

## 1. Overview

This document describes how `backend/` is actually built: package layout, request handling, data access, and security mechanics. For the product-level requirements this service satisfies (domain concepts, functional requirements, API contract, policies), see the root [`SYSTEM_DESIGN.md`](../SYSTEM_DESIGN.md) — this doc is its implementation companion, scoped to "how," not "what/why."

The service is a single Spring Boot 3.4 / Java 21 module (`com.wedding.service`) backed by PostgreSQL, with **no ORM**: every query is hand-written SQL executed through a thin `DataService` wrapper over Spring's `JdbcTemplate`/`NamedParameterJdbcTemplate`. This is a deliberate choice for a small, short-lived domain model — see §12.

## 2. Goals

- Keep the whole backend legible in one sitting: as of this writing it is ~11 small controller/service classes plus three migrations, with no framework-generated boilerplate (no repository interfaces, no entity classes, no mapper layer).
- Make every planner write traceable: any INSERT/UPDATE reachable from `/api/v1/internal/**` records a before/after audit row.
- Fail loudly and uniformly: every error path — business rule violation, bean-validation failure, or unexpected exception — returns the same JSON error shape with a request ID a planner can hand back for debugging.

## 3. Scope

In scope: HTTP API, authentication/authorization, SQL persistence and migrations, CSV import/export, audit logging, local image storage for the public site, and an outbound Slack notification on every RSVP status change (see §5's `SlackNotifier`). Out of scope (owned elsewhere or not yet built): the planner UI (`frontend/internal/`, see its own `SYSTEM_DESIGN.md`), the guest UI (`frontend/public/`, see its own `SYSTEM_DESIGN.md`), and invitation delivery itself (root design §5.6 — delivery is planner-recorded, not sent by this service; the Slack integration is a planner-facing alert, not a guest-facing message).

## 4. Package Layout

```text
com.wedding.service
├── api/       REST controllers, ApiException, ApiErrorHandler, RequestIdFilter
├── service/   DataService (DB access), BootstrapService, MediaService,
│              InvitationCardRenderer (PDF/QR rendering), MediaSeedService, SlackNotifier
├── security/  SecurityConfig, JwtFilter, JwtService, Principal
└── config/    AppProperties (typed config binding), WebConfig
```

There is no `repository`, `model`/`entity`, or `dto` package: controllers query through `DataService` directly and return `Map<String,Object>` (or `List<Map<String,Object>>`) rows straight from SQL, serialized by Jackson. Request bodies use small local `record`s declared inside the controller that needs them (e.g. `AuthController.Login`, `InternalController.PartyInput`) rather than shared DTO classes.

## 5. Request Flow and Controllers

Every request passes through, in order: `RequestIdFilter` (`@Order(1)`, stamps a UUID onto the request and an `X-Request-Id` response header) → Spring Security's filter chain, including `JwtFilter` → the matched `@RestController` method → `ApiErrorHandler` if anything throws.

| Controller | Base path | Responsibility |
| --- | --- | --- |
| `AuthController` | `/api/v1/auth`, `/api/v1/guest/sessions` | Planner login (email/password); guest session (guest name + verification answer) |
| `GuestController` | `/api/v1/guest/**` | Self-service: view party/guests, update editable guest fields, view events, RSVP, view accommodation, file a change request |
| `InternalController` | `/api/v1/internal/**` | Planner writes: create party/guest, issue QR invitation, record delivery, create event/venue/venue-room/venue-fee/accommodation-assignment/things-to-do-item records, manual RSVP override |
| `InternalDataController` | `/api/v1/internal/**` | Planner reads (dashboard, list/detail endpoints, including nested `venue → {rooms, fees}`, the flat cross-venue `venue-rooms` list, and `party → guests` with each guest's room-assignment join) plus **generic** update/archive for simple lookup-style resources, plus site-settings read/update |
| `GuestImportController` | `/api/v1/internal/guests` | CSV bulk guest import + downloadable import template |
| `ReportController` | `/api/v1/internal/reports` | CSV exports (attendance, dietary, guest list, rooming) |
| `SiteController` | `/api/v1/guest/site` | Guest-facing public-site reads: config (settings + visible pages), schedule, things-to-do items, FAQ items, travel (hotels + flights) — kept separate from `GuestController` so its `public_visible` filter never touches which events a party can RSVP to |
| `MediaController` | `/api/v1/internal/media`, `/api/v1/media/{id}` | Image upload/list (planner-only) and unauthenticated image read (an `<img src>` can't send a Bearer header) |
| `InvitationCardController` | `/api/v1/internal/parties/{id}/invitation-card.pdf`, `/api/v1/internal/invitation-cards.pdf`, `/api/v1/internal/invitation-cards/issue-missing`, `/api/v1/internal/invitation-cards/preview.pdf` | Renders printable, two-sided A6 QR invitation cards: two PDF pages per party (front, back), alternating across the whole document so a duplex printer auto-collates correctly. The front is `site_settings.invitation_front_image_id`, cover-cropped full-bleed, nothing else drawn on it; the back is `invitation_back_image_id` plus the QR/invite-URL/guest-name elements positioned via `invitation_card_layout` (jsonb). Kept separate from `InternalController` (which mints the underlying tokens) since PDF generation is a distinct concern with its own failure modes. The two `GET` PDF endpoints never mutate: if any non-archived party lacks a printable token they fail with `409 MISSING_INVITATION(S)` rather than silently minting one — the planner calls `issue-missing` explicitly first, which mints tokens only for parties that don't have one yet. `preview.pdf` (`POST`, `?side=FRONT\|BACK\|BOTH`, default `BOTH`) overlays a candidate (unsaved) card design onto the DB-loaded theme and renders one sample card inline; `renderer.render(..., Side)` emits only the requested side's page(s) so the planner UI can fetch front and back as two separate single-page PDFs for a live preview before Save (fetching a single combined page via a PDF-viewer `#page=` fragment proved unreliable when the same document was embedded in two iframes at once). |

Two implementation patterns are worth calling out because they're not obvious from a single controller in isolation:

- **Generic create.** `InternalController.createSimple(actor, table, input, allowedFields)` backs the venue/venue-room/venue-fee POST endpoints: it filters the request map to an explicit allowed-fields list, inserts, and audits — one method instead of a dozen near-identical ones.
- **Generic update/archive.** `InternalDataController` holds `TABLES` (route resource name → SQL table) and `COLUMNS` (route resource name → editable-column allowlist) maps. `PATCH /internal/resources/{resource}/{id}` and `POST /internal/resources/{resource}/{id}/archive` dispatch through these maps for every simple resource (parties, guests, venues, venue-rooms, venue-fees, events). Guests are the one exception baked into `archive()`: archiving a guest sets `active=false`, not `archived=true`, matching the `guest` table's own soft-delete column. Adding a new simple lookup resource means adding one `TABLES`/`COLUMNS` entry, not a new controller method — extend this pattern rather than writing a bespoke PATCH/archive pair.
- **Enum-column validation.** Both generic write paths (`InternalController.params()` and `InternalDataController.update()`) chain every value through `DataService.checkEnum(key, value)` after `coerceUuidLike`. It normalizes to uppercase and 400s with `VALIDATION_ERROR` on a value outside the column's allowed set (`ENUMS`, keyed by SQL column name — `relationship_group`, `wedding_side`, `attendance_probability`, `passport`, `fee_type`), and maps a blank string to `null`. Without it, a bad enum value would only surface once it hit the underlying `CHECK` constraint, as an opaque `500`. `GuestImportController` reuses the same `DataService.ENUMS` sets (public for exactly this reason) to validate CSV rows up front, joining failures into the same batch `IMPORT_INVALID` error rather than letting a bad row 500 mid-insert.

Endpoints with real business logic (RSVP status transitions, accommodation capacity, CSV import validation) are written out individually rather than genericized, since their rules differ per-endpoint.

- **Outbound Slack notification on RSVP.** Both RSVP write paths — `GuestController.rsvp` and `InternalController.manualRsvp` — call `SlackNotifier.rsvpRecorded(rsvpId)` after their `UPDATE`. One message is posted per RSVP status change (including a change back to `PENDING`) — there is no per-party deduplication, so a household RSVPing guest-by-guest produces one message per guest. Inside `GuestController.rsvp`'s `@Transactional` method the actual HTTP POST is deferred to `TransactionSynchronizationManager`'s `afterCommit` callback, so a rollback can't announce an RSVP that never happened; `InternalController.manualRsvp` isn't transactional, so it posts inline. The message is built by `SlackNotifier.buildPayload`, a pure function (package-visible, unit-tested in `SlackNotifierTests` without Spring or a real webhook): the payload has no top-level `text`, only two `blocks` (Slack's actual key — see the RSVP notification decision log entry for why not `"block"`) — a `header` block whose `plain_text` reads `"RSVP: {name} from {party} party responded {STATUS}"` (`STATUS` is the raw `rsvp.status` enum value, e.g. `ATTENDING`, not a human word), and a `section` block whose `mrkdwn` text is always `"*Notes*: "` with `rsvp.note` appended verbatim (blank when there is none) so a guest's or planner's note is visible without opening the planner UI. The target URL is `wedding.slack.webhook-url` (`SLACK_WEB_HOOK` in `.env`, never committed); the integration silently no-ops if unset or `wedding.slack.enabled=false`, and any HTTP failure is caught and logged — Slack downtime must never fail the RSVP request itself.

**Request-body key convention is not uniform — this has caused real bugs.** Endpoints backed by a typed `record` + `@Valid @RequestBody` (`PartyInput`, `GuestInput` in `InternalController`, and the event-create endpoint's `Map` access via `in.get("venueId")`/`in.get("startsAt")`) bind/read **camelCase** keys, because that's the Java field name Jackson matches against. Endpoints backed by `createSimple` or the generic `PATCH /internal/resources/{resource}/{id}` take a raw `Map<String,Object>` filtered against a `Set<String>` of **snake_case** SQL column names, because those keys are used as literal column/parameter names. Every read endpoint returns raw SQL rows, so responses are snake_case throughout — only *some* writes are camelCase. A client that generalizes "the API is snake_case" from the read endpoints will silently 400 (validation failure on a record) or 500 (missing named SQL parameter) on `POST /internal/parties`, `POST /internal/parties/{id}/guests`, and `POST /internal/events`. When adding a new record-backed endpoint, either accept this split and document it at the call site, or bind camelCase-in/snake_case-out consistently — don't add a third convention.

## 6. Data Access

`DataService` (`service/DataService.java`) is intentionally ~20 lines:

- `one(sql, params)` — runs a named-parameter query, throws `ApiException(404, "NOT_FOUND")` if it returns no rows, otherwise returns the first row as a `Map<String,Object>`.
- `many(sql, params)` — same, returns the full row list.
- `audit(actor, action, entityType, entityId, before, after)` — serializes `before`/`after` to JSON (via the shared Jackson `ObjectMapper`) and inserts into `audit_record`. Called after essentially every planner-initiated write.
- `uuid()` / `id(value)` — UUID generation and parsing helpers used instead of relying on the driver's UUID handling everywhere.
- `hashToken(value)` — SHA-256 + Base64, used as `invitation.token_hash`, the unique column looked up on every guest login and lookup call. `newToken()` mints the 8-char raw token itself (see §12). `invitation.token` (added in `V4`) additionally retains the raw value — see §12's design-decision entry for why, and never `SELECT * FROM invitation` or add `"invitation"` to `InternalDataController.TABLES`, both of which would leak that column into a response or an audit before/after snapshot via a *generic*, unreviewed path — `InternalDataController.party()` deliberately selects `i.token` as one explicit column among others (no `db.audit(...)` call on that read path), which is the intentional exception: an admin viewing one party's own invitation, not a blanket leak.
- `passwords` — a shared `BCryptPasswordEncoder`, used for planner passwords and for party verification answers (case-insensitive: answers are lowercased/trimmed before hashing and before comparison).

Controllers build `NamedParameterJdbcTemplate`/`MapSqlParameterSource` calls directly; there is no query-builder or criteria API. Nullable/optional filters are expressed as `(:param IS NULL OR column = :param)` (see `ReportController.attendance`) rather than conditionally constructing SQL strings, except where the WHERE clause itself needs to change shape (e.g. `InternalDataController.rsvps` appends a clause only when `eventId` is present).

Schema changes go through Flyway migrations in `src/main/resources/db/migration/` (`V1__initial_schema.sql`, `V2__planner_ui_lifecycle.sql`, `V3__public_site.sql`, `V4__invitation_cards.sql`, `V5__things_to_do.sql`, `V6__venue_and_guest_metadata.sql`, `V7__merge_accommodations_into_venue.sql`, `V8__more_site_images.sql`, `V9__venue_image_field_cleanup.sql`, `V10__rsvp_party_invite_integrity.sql`, `V11__invitation_card_background.sql`, `V12__invitation_card_layout.sql`, `V14__invitation_card_field_color.sql`, `V15__invitation_card_invite_url_field.sql`, `V16__drop_budget_module.sql`, `V17__invitation_card_two_sided.sql`, `V18__site_content_cleanup.sql`, `V19__guest_attendance_probability_na.sql`, `V20__universal_event_eligibility.sql`, `V21__site_layout_toggle.sql`, `V22__site_styling_and_home_design.sql`, `V23__tile_styling.sql`, `V24__guest_login_throttle.sql`); per project convention, past migrations are never edited — see root `CLAUDE.md`. Note the gap at `V13`: it briefly existed as `V13__party_slack_notified.sql` (a `party.slack_notified_at` claim column for a since-dropped once-per-party Slack dedup rule — see the RSVP notification decision log entry) and was deleted before ever being applied anywhere, so the number is skipped rather than reused. Flyway only requires strictly increasing versions, not contiguous ones, so this is safe — just don't add a new `V13` file. `V1` establishes the full domain schema in one file (parties, guests, invitations, events, venues, RSVPs, accommodations, budget, FX snapshots, audit); `V2` is a small additive migration (archived flags on lookup entities, a partial unique index on active guest email); `V3` adds the public-site tables (`media_asset`, `site_settings` — a singleton row enforced by a `CHECK` constraint on a `UNIQUE` boolean column, `site_page`, `travel_item`) and an `event.public_visible` flag independent of RSVP eligibility; `V4` adds `invitation.token` (the raw, recoverable QR token) and four `site_settings` columns for the invitation card's artwork and text (`invitation_image_id`, `invitation_headline`, `invitation_body`, `invitation_footer`); `V5` drops `travel_item` (the Travel tab is now a single free-text body on `site_settings`) and replaces it with `thing_to_do_item` (category, title, description, optional image) plus a `things_to_do_heading`/`things_to_do_body` pair on `site_settings`, and flips the previously-hidden `things-to-do` `site_page` row visible; `V6` adds venue-comparison columns to `venue` (`location`, `distance_from_ktm_km`, `transportation_required`, `room_block_min`/`max`), two new child tables `venue_room` and `venue_fee`, eight guest list-building columns including `room_assignment_id` (originally a `REFERENCES accommodation_room(id)`, separate from the formal `accommodation_assignment` table — see §12), and constrains the previously-free-text `guest.relationship_group` with a `CHECK`, normalizing existing values first; `V9` drops unused venue comparison fields (`location`, `pricing`, `food_score`, `view_score`) and adds `venue.image_id`; `V10` adds `rsvp.created_at` (waitlist FIFO ordering) and denormalizes `rsvp.party_id` onto the table so a composite FK to `event_eligibility(event_id, party_id)` can enforce that an rsvp row only exists while its party is invited to the event — see §12; `V11` repoints the seeded invitation background (old Himalayas artwork → save-the-date design) on upgrade, only if the column still holds the old seeded id; `V12` replaces `invitation_headline` with `invitation_header1`/`invitation_header2`, adds `invitation_card_layout` (jsonb — per-field font/size/Y plus the QR's X/Y/size, see §12) with a default modeled on `card.jpg`'s hand-drawn layout, and repoints the seeded background again (→ `card.jpg`) the same way `V11` did; `V14` backfills a `color` (hex) key into every field object already stored in `invitation_card_layout` via chained `jsonb_set(..., true)` calls, so an existing customized layout keeps its font/size/Y while gaining the new planner-editable text color; `V15` merges the separate `hostLine`/`tokenLine` fields into one `inviteUrl` field (deletes both jsonb paths, adds the merged one) and brings the column's own stale `DEFAULT` clause up to date with `V14`'s color addition and this merge, since it was previously unreachable-but-stale (see §12); `V16` drops the budget module and its FX-rate-snapshot support entirely (`budget_line_item_contributor`, `budget_line_item`, `budget_category`, `budget_contributor`, `fx_rate_snapshot`) — the feature had no consumer beyond the planner UI's Budget page, which was removed in the same change. ## 7. Error Handling

`ApiException` is a typed `RuntimeException` carrying an HTTP status and a machine-readable `code` (e.g. `NOT_FOUND`, `INVALID_CREDENTIALS`, `ROOM_CAPACITY`, `RSVP_CLOSED`) — controllers throw it directly for business-rule violations rather than returning error DTOs. `ApiErrorHandler` (`@RestControllerAdvice`) maps three cases to a consistent JSON body (`code`, `message`, `requestId`, plus `errors` for validation failures):

1. `ApiException` → its own status/code.
2. `MethodArgumentNotValidException` (bean-validation failures on `@Valid @RequestBody`) → `400 VALIDATION_ERROR` with a per-field error list.
3. Anything else → `500 INTERNAL_ERROR`, logged server-side with the full stack trace (never leaked to the client), correlated via the `requestId` set by `RequestIdFilter`.

## 8. Authentication and Security

- **Token format.** JWTs are hand-rolled in `JwtService` (HMAC-SHA256, base64url header/claims/signature, no external JWT library) rather than using a library like `jjwt`. Claims are `sub` (subject UUID), `role`, `partyId` (guest tokens only), and `exp`. Signature verification uses `MessageDigest.isEqual` for constant-time comparison. This keeps the dependency footprint minimal for a two-flow, single-secret auth model — reach for a real JWT library first if claims, algorithms, or key rotation ever need to grow beyond this.
- **Two issuance paths**, both in `AuthController`, both ultimately calling `JwtService.create(...)`:
  - Planner login: email/bcrypt-password against `planner_user`, issues an 8-hour (`wedding.security.planner-session-minutes`) token with `role` = `ADMIN`/`PLANNER`.
  - Guest session: rate-limited (see `GuestLoginThrottle` below) guest **name** + bcrypt-verified answer against the party's `verification_answer_hash`, issues a 30-day (`guest-session-minutes`) token with `role=GUEST` and `partyId` set. A first-time guest login also flips the invitation from `DRAFT` to `VIEWED`. `AuthController.resolveParty()` maps the name to a party: case-insensitive and whitespace-collapsed (`normalizeName`) match on `first_name || ' ' || last_name` across active guests of unarchived parties with a live, non-`CLOSED` invitation, falling back to first name alone if the full-name match finds nothing. Zero matches → `404 GUEST_NOT_FOUND`; matches spanning more than one party → `409 AMBIGUOUS_NAME` (never a guess, which would leak one party's question to another's guest). The same resolution backs `/guest/invitations/lookup`, so both steps of the guest gate agree. The name is an identifier, not a secret — the verification answer remains the only access factor, which is why it is throttled.
- **`GuestLoginThrottle`** defends that single low-entropy answer, per party, with state in `guest_login_throttle` (`V24`) rather than in memory — so limits survive a restart and hold across API instances. Three tiers: **5 answers per rolling minute** (`429 RATE_LIMITED`), **5-minute lock at 10 consecutive failures** and every further multiple of 10 (`429 TEMPORARILY_LOCKED`), **permanent lock at 30** (`403 ACCOUNT_LOCKED`), cleared only by `POST /api/v1/internal/parties/{id}/unlock` (ADMIN-only). A correct answer resets all three. `/guest/invitations/lookup` calls `assertNotLocked()` — a read-only check that consumes no attempt — so a locked-out guest is told why at the name step instead of after typing an answer. Counting is per party, not per guest: every guest in a party shares one answer, so a per-guest counter would just multiply the attacker's budget.
- None of the throttle methods is `@Transactional`, deliberately: each one increments a counter and then throws on it, and a rollback would undo the very increment the limit depends on, leaving an attacker with unlimited attempts. Each statement self-commits, and the counter updates are single atomic `UPDATE ... RETURNING` statements, so concurrent attempts still can't both read a stale count.
- **`JwtFilter`** runs before Spring's `UsernamePasswordAuthenticationFilter`, reads `Authorization: Bearer <token>`, and — if it parses — sets a `Principal` (record: `id`, `role`, `partyId`) as the authenticated principal with a single `ROLE_<role>` authority. An invalid/expired token is *silently* left unauthenticated (caught `IllegalArgumentException`) rather than rejected at the filter; authorization then denies the request downstream based on `SecurityConfig`'s matchers.
- **`SecurityConfig`** registers a `CorsConfigurationSource` bound to `wedding.cors.allowed-origins` (`WEDDING_CORS_ALLOWED_ORIGINS`, comma-separated) but only calls `http.cors(...)` to actually wire it into the filter chain when that list is non-empty. This matters when a frontend is served from a different origin than the API (e.g. Render static sites). Registering the CORS filter unconditionally with an empty allow-list breaks local/Docker Compose: browsers send an `Origin` header on same-origin fetch/XHR requests too, and once Spring Security's CORS filter is active it 403s any request whose `Origin` isn't allow-listed — before `authorizeHttpRequests` even runs. Leaving the filter out entirely (empty list) preserves the pre-CORS behavior of ignoring `Origin` altogether.
- **`SecurityConfig`** is stateless (no HTTP sessions, CSRF disabled since there's no cookie-based auth), sets a `default-src 'self'` CSP header, and authorizes by path prefix: `POST /api/v1/internal/parties/*/unlock` → `ADMIN` only (listed first so it narrows the rule below it — clearing a brute-force lock shouldn't be something any planner can do on a phone call), `/api/v1/internal/**` → `ADMIN`/`PLANNER`, `/api/v1/guest/**` → `GUEST`, everything else denied except the explicit public list (health check, Swagger UI, `/api/v1/auth/**`, `/api/v1/guest/sessions`, `/api/v1/guest/invitations/lookup`, `/api/v1/media/**`). The last two exist because `anyRequest().denyAll()` blocks anything not explicitly listed: the name lookup has to run *before* a guest session exists (it shows the verification question), and image reads have to work from a plain `<img src>`, which can't carry a bearer token. Both matchers must be listed ahead of the `/api/v1/guest/**` → `GUEST` rule to take effect; `/api/v1/media/**` sits outside that prefix entirely so it never collides with it.
- Party-level isolation for guests is enforced in SQL, not in the security layer: every `GuestController` query filters by `p.partyId()` from the parsed token, so a valid guest token can only ever reach rows belonging to its own party.
- `BootstrapService` (an `ApplicationRunner`, gated by `wedding.bootstrap-enabled`, default on) seeds exactly one `ADMIN` planner user from `wedding.bootstrap-admin.*` config if `planner_user` is empty — this is how the first login exists in a fresh environment.
- Both `InvitationCardController` PDF endpoints sit under `/api/v1/internal/**`, so they inherit the existing `ADMIN`/`PLANNER` matcher with no `SecurityConfig` change. They are deliberately **not** given the `/api/v1/media/**`-style public exemption: a bulk card PDF contains every printable party's factor-one credential, so making it fetchable by URL alone would be the worst regression available in this codebase.

## 9. Startup Seeding

`MediaSeedService` is an `ApplicationRunner`, gated by the same `wedding.bootstrap-enabled` flag as `BootstrapService` (matters because `WeddingServiceApplicationTests` sets that flag `false` against a schema-less H2, and this runner queries `media_asset`/`site_settings`, which don't exist there). On boot it seeds three bundled images into `media_asset` and the local media directory under fixed UUIDs — a Himalayas line drawing (`resources/seed/invitation-card-default.jpg`) and the original save-the-date design (`resources/seed/invitation-background-default.jpg`), both kept around in the media library for manual reuse, and `card.jpg` (`resources/seed/invitation-background-v2.jpg`), the current invitation card **front** default — then points `site_settings.invitation_front_image_id` at that current default, but only while the column is still `NULL`, so a planner's own choice is never overwritten on restart. There's no seeded default for `invitation_back_image_id` — a blank white back with just the QR/text elements is a reasonable out-of-the-box state, and unlike the front there's no obvious single "generic" back image to ship. `V11__invitation_card_background.sql` and `V12__invitation_card_layout.sql` each clear the column's *previous* seeded value on upgrade (only if it still points at that specific old asset id), so existing installs pick up each new default the same way a fresh one does without a `MediaSeedService` code change alone being able to move a planner off their own choice.

## 10. Non-Functional Notes

- Response shape is uniform `Map<String,Object>`/`List<Map<String,Object>>` JSON, not versioned DTOs — acceptable at this scale (root design §9: ~200 guests, ~5 planners, correctness/simplicity over throughput) but means a column rename in SQL is a wire-format change; grep controllers for the column name before renaming one.
- Every planner-writable table that matters for reporting/accountability is archived (soft-deleted), never hard-deleted, so history and audit rows stay valid.
- `application.yml` binds every tunable through `AppProperties` (`wedding.security.*`, `wedding.bootstrap-admin.*`, `wedding.media.*`, `wedding.slack.*`) with environment-variable overrides and local-dev defaults — there is no scattered `@Value` usage.

## 11. Technology and Build

- **Framework:** Spring Boot 3.4.2, Java 21 (Gradle toolchain-pinned).
- **Dependencies:** `spring-boot-starter-web`, `-security`, `-jdbc`, `-validation`, `-actuator`; `flyway-core` + `flyway-database-postgresql`; `springdoc-openapi-starter-webmvc-ui` (Swagger UI at `/swagger-ui.html`); `postgresql` driver at runtime. No ORM (`spring-boot-starter-data-jpa` is intentionally absent). `com.google.zxing:core` + `org.apache.pdfbox:pdfbox` render invitation cards: ZXing's `Encoder` produces a `ByteMatrix` that's drawn straight into the PDF as vector rectangles rather than rasterized through `zxing:javase`, so the QR stays crisp at any print resolution and the extra artwork-rendering dependency isn't needed.
- **Testing:** `spring-boot-starter-test` + `spring-security-test`, with `h2` as an in-memory test-only database (`postgresql` also available at test runtime for dialect compatibility). No Mockito — tests are `@SpringBootTest` integration tests against H2 per `application-test.yml`, run with `./gradlew test`.
- **Build/deploy:** multi-stage `Dockerfile` — `gradle:8.12-jdk21` builds a boot JAR (`gradle bootJar`), then `eclipse-temurin:21-jre` runs it. In the compose stack this is the `api` service; Postgres and the Nginx-served planner UI are the other two.
- **Remote debugging:** the `api` service's container exposes a JDWP port (`5005`, `EXPOSE`d in the `Dockerfile`), enabled via `JAVA_TOOL_OPTIONS` in `compose.yaml` (`-agentlib:jdwp=...,suspend=n,address=*:5005`) rather than baked into the image, so debug wiring stays out of the JAR and only applies when run through this compose file. `suspend=n` means the app starts normally regardless of whether a debugger ever attaches. Point an IDE's remote-debug config at `localhost:5005`. JDWP has no authentication, so never publish 5005 on a host reachable from outside your own machine.

## 12. Design Decisions

- **No ORM, no repository layer.** With ~15 tables, hand-mapped `Map<String,Object>` rows, and short-lived project scope, an ORM's mapping/lazy-loading machinery is overhead this codebase doesn't need. If the schema or query complexity grows substantially past its current size, revisit this — it is a fit-for-scale choice, not a permanent constraint.
- **Hand-rolled JWT over a library.** Two flows, one signing secret, four claims — a full JWT library's algorithm negotiation and key-rotation support isn't exercised here. `JwtService` should stay this simple; if requirements grow (multiple keys, asymmetric signing, refresh tokens), switch to a real library rather than extending the hand-rolled implementation.
- **Generic resource endpoints over one-per-entity CRUD.** §5's `createSimple`/`TABLES`+`COLUMNS` pattern trades some type safety (editable fields are an allowlist `Set<String>`, checked at runtime, not the compiler) for not having a dozen near-identical controller methods. New *simple* lookup resources should extend the existing maps; entities with real business rules (RSVP, accommodation assignment) should keep their own explicit endpoint.
- **RSVP capacity enforcement differs by actor.** A guest RSVPing themselves to `ATTENDING` on a full event is silently redirected to `WAITLISTED` (`GuestController.rsvp`) — guests cannot choose to overbook. A planner's manual RSVP override (`InternalController.manualRsvp`) does not re-check capacity at all, since planners are trusted to manage waitlist promotion deliberately (root design §5.3).
- **Accommodation capacity is checked, and overridable, at write time.** `InternalController.assignment` sums already-booked occupants for the room across the requested date range and rejects the insert with `409 ROOM_CAPACITY` unless `override_capacity` is set, in which case the audit action itself changes to `OVERRIDE_CAPACITY` instead of `CREATE` — the override is visible in the audit trail without a separate flag to check. The capacity lookup targets `venue_room.capacity`, which is nullable (a room-block quoting row may have no fixed capacity); a `null` result 409s with `ROOM_CAPACITY` rather than NPE-ing on the unboxing. `V7` also fixed a real bug here: the INSERT unconditionally referenced `:party_id`/`:guest_id`/`:coverage_notes`, but `params(in)` only binds keys the request body actually contains, and the Assignment form never sent `guest_id` — every assignment created from the UI 500'd (confirmed against a live environment: `accommodation_assignment` had zero rows despite the UI being fully wired up). Fixed by explicitly binding all three as `null` when absent; the existing `cast(:party_id as uuid)`/`cast(:guest_id as uuid)` wrapping already makes a bound `null` resolve correctly, and Postgres infers `coverage_notes`' type from the INSERT's target column for an unspecified-type null parameter.
- **CSV import validates before writing anything.** `GuestImportController` parses the whole file, collects every row-level error (missing required column, missing required field, duplicate active email) up front, and throws a single `400 IMPORT_INVALID` with all errors joined if any exist — it never partially imports a batch.
- **Media storage is local disk, not object storage.** `MediaService` writes uploaded images to a configured directory (`wedding.media.dir`, a Docker volume in compose) keyed by the `media_asset` UUID, and `MediaController` streams them back by ID. This matches the rest of the stack's "small, self-contained deployment" posture — an S3-compatible store is the natural upgrade if the app ever needs multi-instance/horizontal scaling, since local disk doesn't survive a container being replaced without the volume.
- **Venue cost is two child tables, not one table with a kind discriminator.** `venue_room` (occupancy, room count, Nepali/foreigner nightly rate) and `venue_fee` (a named charge and an amount) describe unrelated shapes — a discriminated `venue_expense` table would leave half its columns `NULL` on every row and need a `CHECK` tying `kind` to which columns may be set. Two tables cost one extra `TABLES`/`COLUMNS` entry and one extra create endpoint, both already cheap under the generic-resource pattern. Rates are stored as plain NPR `NUMERIC` — no currency column — since both tiers (Nepali/foreigner) are quoted in NPR by every venue in scope; revisit if a venue ever quotes in USD.
- **Guest `room_assignment_id` is a separate FK from `accommodation_assignment`.** `accommodation_assignment` is the confirmed booking record (check-in/out dates, status, capacity-checked at write time). `guest.room_assignment_id` is a lighter planning-stage pointer straight at `venue_room` for sketching out who's staying where before a formal assignment exists — it deliberately does **not** go through the capacity check in `InternalController.assignment`, so it can hold a placeholder pairing that gets firmed up into a real `accommodation_assignment` later. The two are allowed to disagree; the rooming-list report (`ReportController.rooming`) still reads only from `accommodation_assignment`.
- **`accommodation_property`/`accommodation_room` were merged into `venue`/`venue_room` (`V7`).** The wedding venue is now the hotel itself, so a lodging place and its rooms no longer needed a separate entity pair from the venue-comparison one added in `V6`. `accommodation_property`'s columns were already a strict subset of `venue`'s. `venue_room` already generalized "a room" to "a room type with N available" for cost quoting; a specific bookable room is just the special case where the new nullable `room_number` (`UNIQUE(venue_id, room_number)`) is set and `max_available` isn't tracked — both flavors coexist in one table. The migration reuses each source row's original `id` when copying it into `venue`/`venue_room`, so every existing `accommodation_assignment.room_id` and `guest.room_assignment_id` value stayed valid with zero row rewrites — only the FK's target table changed (`ALTER TABLE ... DROP CONSTRAINT ... ADD CONSTRAINT ... REFERENCES venue_room(id)`). `accommodation_assignment` and `accommodation_change_request` were **not** folded into anything — they keep their own booking/change-request concept, just repointed. The Accommodations planner page kept its own route (rather than folding Assignments/Change Requests into `VenueDetailPage`) because the dashboard links to it for the open-change-request count, and a rooming list is inherently cross-venue.
- **`event.public_visible` is independent of RSVP collection.** `public_visible` controls whether an event shows on the public Schedule tab; every party is always able to RSVP to every event regardless. Keeping this as its own column lets a planner stage an event's RSVP collection before announcing it publicly, without special-casing the RSVP guest API.
- **Every party attends every event; a guest responds — `rsvp` is a derived projection of `event_eligibility × active guests`, kept in sync by `DataService.syncRsvps` (`V10`, `V20`).** Per-event invitations were dropped (there is no planner-facing invite/un-invite action any more); `event_eligibility` stays in the data model only because `rsvp`'s composite FK to it enforces "an rsvp row only exists while its party and event both exist" (see `rsvp_eligibility_fk`, `V10`), so instead of being dropped it's maintained as an insert-only invariant: every party × every event. `syncRsvps()` first backfills `event_eligibility` to the full cross-product (`INSERT ... ON CONFLICT DO NOTHING`, never deletes — so archiving an event never destroys its recorded RSVPs), then reconciles `rsvp` rows against `event_eligibility × active guests` the same way it always did. It's called from every path that changes any of the three inputs: party creation (`InternalController.party`), event creation (`InternalController.event`), guest creation (`InternalController.guest`), guest archive (`InternalDataController.archive`), and CSV import (`GuestImportController.importCsv`, once per batch). `V20__universal_event_eligibility.sql` backfills existing data the same way. The planner UI surfaces the RSVP side of this as a guests × events matrix on the party detail page rather than a standalone cross-party RSVP list — see `frontend/internal/SYSTEM_DESIGN.md`.
- **The guest-side RSVP capacity check is now transactional.** `GuestController.rsvp` previously read the ATTENDING count and wrote the new status as two separate statements with no lock, so two guests racing for the last capacity slot could both read a count under capacity and both write ATTENDING, overshooting it. The endpoint is now `@Transactional` and takes `SELECT ... FOR UPDATE` on the `event` row before counting, serializing concurrent RSVPs to the same event. The planner's manual override (`InternalController.manualRsvp`) still bypasses capacity entirely by design (see above).
- **Invitation tokens are stored recoverable (`invitation.token`), not only hashed.** Printed cards need to be reprintable and the bulk PDF needs to be idempotent, which requires the server to reproduce a party's exact token on demand. Four options were considered: (a) store the raw token in a new column; (b) derive it deterministically via `HMAC(secret, invitationId:version)`, keeping nothing at rest; (c) encrypt it at rest with a dedicated key; (d) never store it, re-issuing on every PDF generation. (a) was chosen. The deciding factor is the threat model, not the token's format: the token is only the first of two access factors (the party's bcrypt-hashed verification answer is the second), and it is printed in plaintext on a card that travels through the postal system — hashing it at rest defended against a database-compromise adversary who, by construction, would already be able to read everything the token protects. (b) and (c) trade that non-benefit for a real one: a lost or rotated key silently bricks every card already mailed, months later, with no test able to catch it in advance. (d) actively breaks the product — reprinting a damaged card, or downloading the bulk PDF twice, would rotate tokens under cards already in the post and reset their `status` back to `DRAFT`. **Invariant to preserve:** never `SELECT * FROM invitation`, and never add `"invitation"` to `InternalDataController.TABLES` — both would leak the raw token into an API response or an audit before/after snapshot. `InvitationCardController`'s `GET` endpoints also never mutate: a party missing a printable token fails the request with `409 MISSING_INVITATION(S)` instead of silently minting one, so a retry, prefetch, or double-click can never rotate a token that's already on a mailed card — issuing one requires the separate, explicit `POST .../issue-missing`.
- **Standard-14 PDF fonts are WinAnsi-encoded.** `InvitationCardRenderer` uses Helvetica/Courier for layout simplicity, but WinAnsi covers Latin-1 plus a handful of extras — no Devanagari, no CJK. Rather than fail mid-render on the 200th page, every card string is preflighted through `PDFont.getStringWidth` before any page is drawn, and an unencodable character throws `422 UNPRINTABLE_TEXT` up front. If non-Latin names become a real requirement, the fix is to embed a subset font (e.g. `PDType0Font.load(doc, notoSansDevanagariBytes, true)`) behind the same font-construction call site — not to special-case individual strings.
- **The invitation card is two-sided (`V17`): a pure-image front and a back carrying exactly three independently-positioned elements.** `invitation_front_image_id`/`invitation_back_image_id` are each cover-cropped full-bleed (uniform scale, centered, overflow clipped, never stretched). The front has nothing else drawn on it. The back carries the QR code, the `inviteUrl` line (`host + "/i/" + token`, one line), and `guestNames` (the party's display name) — each with its own **free x AND y** (not just Y — this replaced the old X-centered-only text model), size, and color via `site_settings.invitation_card_layout` (jsonb: `CardLayout{QrLayout qr, TextLayout inviteUrl, TextLayout guestNames}`). Font is fixed in code for both text elements now (Courier for `inviteUrl`, Helvetica-Oblique for `guestNames`) — no longer planner-editable; text is X-centered on its own x (Y is the baseline, not a true vertical center — documented in the planner UI rather than changed, since a baseline is the natural anchor for single-line PDF text). All three elements render directly over the back artwork with nothing drawn behind them (an earlier auto-toned "plate" rectangle behind them was removed — see `docs/DECISIONS.md`); a planner is responsible for choosing colors/positions with enough contrast against their own artwork, and catches a bad choice in the live preview before printing. `CardLayout.validate(layout, orientation)` (x/y bounds depend on orientation; size bounds; hex color) runs both at render time and inside `InternalDataController`'s `PATCH /site/settings` handler, so a bad value 422s on save rather than only surfacing the next time a card is printed.
- **The QR's own fill color is planner-editable, reversing an earlier "Rejected" decision** (see `docs/DECISIONS.md`) that specifically rejected this to protect scannability. That decision's premise — an auto-toned legibility plate as the safety net — no longer holds, since the plate has since been removed entirely; there is no automatic contrast check anywhere. The live front/back preview is the intended way a planner catches a QR that's become hard to see, before printing — the same trust boundary already given to text color.
- **Orientation (`invitation_orientation`: `PORTRAIT`/`LANDSCAPE`) is one setting for the whole card**, shared by both sides since they're the same physical sheet — it swaps the page between 105x148mm and 148x105mm and every bound `CardLayout.validate()` checks (the QR's own size floor was also raised from a naive 5mm to 20mm here, since anything smaller reliably 422s at render time anyway once a realistic invite URL is encoded — `QR_TOO_DENSE`'s 0.5mm module-size floor). Switching orientation can invalidate already-saved x/y (valid in the old orientation, out of bounds in the new one): the planner UI clamps in-flight values into the new bounds the moment orientation changes, and `InternalDataController.updateSiteSettings()` re-validates the *stored* layout against a *new* orientation whenever one is patched without an accompanying layout update in the same request, so a bypass of the frontend still 422s cleanly instead of silently saving a layout that fails every future render.
- **Site styling/Home-design columns (`V22`) are validated differently from `invitation_orientation`/`site_layout` on purpose.** Those two have a schema `DEFAULT`, so their parse helpers substitute that default on null/blank. The 8 style columns and `home_design_image_id` have none — null means "the guest app's built-in look," a state that must stay reachable — so `parseFontFamilyOrNull`/`parseFontSizeOrNull` return `null` on null/blank rather than defaulting, and `updateSiteSettings`'s color-column branch (`blankToNull`) turns a cleared field's `""` into `NULL` rather than storing a literal empty string (which would otherwise defeat the guest app's `var(--x, fallback)` CSS — see `frontend/public/SYSTEM_DESIGN.md` §6). Font family has no `CHECK` (see the migration note above) while font size does — the same "growing set vs. true closed enum" reasoning already applied to `invitation_orientation`/`site_layout`.
- **Invitation tokens shortened to 8 chars, minted once via `DataService.newToken()`.** Previously each of the two independent minting call sites (`InternalController.invitation()`, `InvitationCardController.issueMissing()`) built its own ~50-char token (`UUID.randomUUID() + "-" + Long.toUnsignedString(random.nextLong(), 36)`) with its own `SecureRandom` field. `newToken()` centralizes this: 6 random bytes, `Base64.getUrlEncoder().withoutPadding()` (alphabet `A-Za-z0-9-_`), exactly 8 chars, ~2.8e14 possible values. No collision-retry logic — at this app's realistic scale (tens to low hundreds of parties) a collision is astronomically unlikely, and `invitation.token_hash`'s `UNIQUE` constraint means a collision would surface as a loud insert failure, never as two parties silently sharing a working invite. Already-issued long-format tokens keep working unchanged (hash comparison is format-agnostic; nothing force-rotates them). Base64url's alphabet has a few visually-confusable characters for a token that's now printed as part of a human-typeable URL (`l`/`I`/`1`, `O`/`0`) — an unambiguous alphabet (e.g. Crockford base32) was considered and rejected in favor of honoring the literal "base64 encoded" requirement, since the QR code remains the primary, redundant way to use the card and manual entry is a fallback path.
